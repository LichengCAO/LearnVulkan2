# Repository Guidelines

## C++ Code Style

- Apply these rules to first-party C++ code. Do not modify code under `external/` to enforce them.
- Prefix every private member function name with a single underscore, for example `_CreateBuffer`.
- Declare every function with a non-`void` return type using trailing return type syntax: `auto Function(...) -> ReturnType`.
- Functions returning `void` are exempt from the trailing return type rule.
- For new and migrated configuration interfaces, use `Set` for required settings without a usable default and `Customize` for optional settings with a usable default. An invalid zero sentinel is not a usable default.

## RHI Creation and Threading

These requirements apply to new and migrated first-party RHI interfaces. Existing interfaces retain their current threading restrictions until audited and migrated; this policy alone does not make them thread-safe.

Objects and allocators have no thread affinity. Unless an interface explicitly documents internal synchronization, callers must exclude conflicting access to the same instance and to any related shared mutable state. Independent instances may be used concurrently.

### Creation

- After device initialization, public object-level `Create()` supports concurrent creation of independent instances by default. The caller must exclude concurrent creation, modification, and destruction of the same instance, and keep creation inputs and dependencies stable for the duration of the call.
- Multiple threads may read the same finalized CreateInfo. Modification, `Reset()`, and `Finalize()` require exclusive access relative to readers and other writers.
- Creation requiring coordination of shared mutable state belongs in a MyDevice creation entry point: `CreateXxx()`, or `GetOrCreateXxx()` for cached objects. The corresponding object does not expose public `Create()`; its implementation may use private `_Create()`.
- Document which shared state each MyDevice creation entry point accesses and any internal synchronization. Otherwise callers synchronize it with all other accesses to that state, including indirect release paths. Operations using independent shared state may run concurrently; synchronization is not automatically global to MyDevice.
- `Create()` completes creation before returning, without implicitly enqueueing work. Keep object-level `Create()` according to its threading contract, regardless of whether it calls Vulkan or how long it takes.

### Release and Shared State

- Destruction and final strong-reference release may run on any thread when callers satisfy the synchronization requirements of every related object. Atomic reference counting does not synchronize object contents or the final release path.
- Unless an interface documents internal synchronization, callers synchronize creation, lookup, release, and whole-cache destruction that access the same MyDevice-managed cache or allocation records. Allocators do not provide internal locking unless explicitly documented.
- Borrowed handle values do not own native resources. Copying, moving, clearing, or destroying such a value does not access its owner or release its native handle; validity ends when the owner reclaims the resource.
- Actual resource release completes synchronously, without introducing a deferred reclamation queue. Synchronize according to the shared state accessed, rather than requiring all operations on a Device to be mutually exclusive.
- MyDevice initialization, destruction, and device recreation require exclusive access relative to related resource operations. Host thread safety does not replace GPU completion synchronization or resource lifetime requirements.
- Document threading contracts for `Allocate()`, `Free()`, `Reset()`, recording, and submission independently of `Create()`. DescriptorPool has no internal locking: callers serialize each pool's allocation, explicit Free and final destruction; independent pools may run concurrently subject to their dependencies' contracts. It returns borrowed VkDescriptorSet handles; copying or clearing a handle does not retain or access its pool. See [descriptor pools](docs/descriptor_pool.md#synchronization) for dependency release requirements.

### Migration Priorities

- ComputeShaderProgram is created synchronously through `MyDevice::CreateComputeShaderProgram` and has no public Create/Destroy/Reset. Callers coordinate the shader-module cache, both layout caches, the compute pipeline cache and the supplied VkPipelineCache with all other accesses. Its destructor releases Host module metadata and calls DestroyPipeline, whose cache search also reads the graphics cache (and the ray tracing cache if earlier searches miss); synchronize those accesses too. Destroy the Program before Device teardown and complete native uses first; it does not wait for the GPU or retain submitted work.
- Compute, Graphics and RayTracing ShaderProgram creation is synchronous through the corresponding `MyDevice::Create...ShaderProgram` entry point. Programs expose no public Create/Destroy/Reset, are noncopyable and nonmovable, and release owned resources from their destructor. Caller synchronization remains required for shared cache accesses, indirect release paths and conflicting access to one Program; Graphics lazy `GetVkPipeline` also mutates per-Program state. Program destruction does not wait for GPU work or retain submitted resources.
- ShaderModule is internal and borrows a native handle from the Device cache while retaining its own immutable reflection snapshot. It has no Create/Destroy; wrapper cleanup accesses Host data only. All Program creation paths share the externally synchronized shader-module cache; Graphics lazy creation uses previously obtained handles. Native modules remain cached until Device teardown, after pipeline-cache cleanup. When changing module acquisition, cache keys, reflection lifetime or Program retries, read [ShaderModule ownership](docs/resource_lifetimes.md#shader-module-ownership).
- Rendering uses finalized `RenderPassDesc` and borrowed `FramebufferDesc` snapshots. MyDevice internally serializes its render-target cache lookups, native creation, publication and teardown with a dedicated mutex; other Program caches retain their caller synchronization requirements. Callers retain attachment resources through preparation, recording and GPU completion, using `KeepAlive(Image/ImageView)` when commands should retain them. When changing descriptions, cache keys, command preparation or attachment release, read [rendering ownership](docs/resource_lifetimes.md#rendering-descriptions-and-native-cache).
- CommandPool keeps public Create/Reset/AllocateOrGetCommandBuffer and owns its native pool through RAII, with no public Destroy. Independent pools may be created and used concurrently; callers exclude conflicting access to one pool and its command buffers, and complete GPU use before Reset or destruction. Device must outlive every pool. When changing allocation, reuse or FrameSlot pool ownership, read [command pool ownership](docs/resource_lifetimes.md#command-pool-ownership).
- Buffer keeps public Create and owns its native buffer and allocation through private storage, with no public Destroy. VMA internal synchronization remains enabled; independent Buffers may create, map, write, create views and release concurrently. Callers exclude conflicting access to one Buffer/allocation/view cache and keep Device/allocator alive through final release. When changing allocation, mapping, movement or cleanup, read [buffer ownership](docs/resource_lifetimes.md#buffer-ownership).
- Buffer inline upload/download uses mapped copies for coherent Host memory. Other memory requires the matching transfer usage and a synchronous GPU copy. Default staged transfers run on COMPUTE from any thread. Explicit transfers use the caller's context/queue and its ownership contract. Synchronize first-party queue Host access by native queue handle, including aliased roles.
- Image keeps public Create for an empty target and has no public Destroy. Independent ordinary Images may create, cache views and release concurrently using VMA synchronization; one Image/cache or ImageView wrapper still requires caller exclusion. ImageResource owns the native image and allocation, so external views and command/descriptor references can outlive the facade. Swapchain imports retain their generation without owning the VkImage or a VMA allocation; swapchain operations/final generation release keep their external synchronization contract. When changing creation, view caching, imports or final release, read [image ownership](docs/resource_lifetimes.md#image-values-and-resource-versions).
- BottomLevelAccelStruct and TopLevelAccelStruct keep synchronous public Create for an empty target, with no public Destroy. Shared private storage owns each native AS and backing Buffer, releasing them in that order with saved creation dependencies and no GPU wait. Independent AS instances may create and release concurrently; same-instance conflicts and Device/allocator teardown require caller exclusion. BLAS Limits contain only ordered size-query capacities/formats/flags; TLAS requires positive SetMaxInstanceCount. GetMemoryRequirements returns saved requirements. BuildAccelStructCommandInput combines target/data selection transactionally, snapshots Host metadata without strong resource references, clears source on reselection and preserves scratch until the description is cleared with assignment from {}. Ordinary AS CreateInfo and CommandInput expose no Reset. The span Build command validates independent tasks atomically before appending one native batch; recording performs no queries, uploads or allocations. Callers preserve borrowed AS/buffer lifetimes, GPU UPDATE history and hidden instance dependencies. TopLevelAccelStructBuildInfo::CommitToDeviceInline remains an explicit static upload of raw-address instance descriptions. When changing AS creation, build metadata or cleanup, read [BLAS ownership](docs/resource_lifetimes.md#blas-ownership) and [TLAS ownership](docs/resource_lifetimes.md#tlas-ownership).
- ShaderBindingTable keeps synchronous Create for an empty target, with no public Destroy. It owns its backing Buffer and copied Host records/group metadata through RAII, remains noncopyable/nonmovable and is not RefCounted. Independent SBT instances may create, edit, Commit and release concurrently; exclude conflicting operations on one SBT, keep Device/allocator/cached properties stable and complete GPU uses before release. TraceRays commands borrow its regions without retaining the SBT. When changing table preparation, upload or lifetime, read [SBT ownership](docs/resource_lifetimes.md#sbt-ownership).

- CLAS and Cluster BLAS batches use synchronous Host Create and Buffer RAII. Single CLAS owners expose IsValid, GetDeviceAddress and GetMemoryRequirements as saved Host queries; validity means allocated storage, not GPU build completion. Packed GPU records/counts may be shader-produced; CommitToDeviceInline remains an optional synchronous CPU convenience. Query allocation requirements through operation-specific static `GetXxxMemoryRequirements(limits, maxCount)` or Compute Sizes `GetXxxBuildScratchBufferSize(limits, maxCount)` and `GetScratchAlignment()`; static `GetXxxBuildInfoBufferSize(maxCount)` uses only Host ABI data. CommandInputs atomically bind complete targets and snapshot operation, limits, maximum count and borrowed addresses without memory requirements or per-destination allocation ranges. Batch Create caches underlying storage/reference Buffer addresses, including explicit table offsets, as private Host metadata; destination owners and tables remain strongly retained by the Batch. Target selection, append and recording query no native sizes/properties or Buffer device addresses. Callers guarantee AS/scratch capacity, device-specific alignment and nonconflicting allocation ranges; Host checks retain completeness, positive capacities, required addresses, fixed ABI alignment/overflow and known task/count/output-array overlaps. Scratch addresses are literal; use zero for zero required scratch. Reselection preserves arguments/scratch/count and clears optional implicit size output; failure preserves the previous target. Copies/moves retain no resources and moved-from targets are invalid. Compute sizes writes packed uint32_t sizes for direct CLAS, Template, instantiate and Cluster BLAS; implicit builds optionally write sizes. The producer bounds optional GPU counts and consumers use only the active prefix. TemplateBatch Create only queries and allocates from explicit capacities; template tasks build through explicit implicit-destination commands. Owners keep no CPU mirror of GPU-produced tables/topology or GPU-ready state. Synchronize dependent GPU reads and perform optional Buffer readback explicitly. Retain templates through instantiation and source CLAS through dependent BLAS use. When changing static queries, target bindings, template publication, task encoding, capacities, outputs or the pipeline opt-in, read [cluster batch ownership](docs/resource_lifetimes.md#cluster-acceleration-structure-batches).

- PTLAS has synchronous Host-only Create and Buffer RAII, independently negotiated NV support and no KHR handle. Required slot/ordinary-partition/per-partition capacities are positive; global capacity defaults to zero. Save build flags and partition translation for identical query/build inputs. CommandInput snapshots target plus mandatory GPU operation/count addresses transactionally, clears source on reselection, preserves scratch and has no Reset. Source compatibility includes all creation options. Recording emits one native build with buildScratchSize and performs no queries/uploads/allocations/submissions/waits. The outer table always provides 72 bytes (max three unique operations); Host helpers encode the published ABI independently of owners. Producer bounds GPU counts, indices/occupancy and UPDATE history; callers synchronize and retain all borrowed resources. Compute-capable queues and outside-rendering recording are required; CLAS pipeline opt-in does not apply. When changing this path, read [PTLAS ownership](docs/resource_lifetimes.md#partitioned-tlas-ownership).

- Audit remaining shared-cache creation paths. Move creation into MyDevice or restructure the shared state according to the actual concurrency requirements. CommandPool creation has no Device registration table; Buffer/Image allocations travel with their resource owners instead of shared maps.
